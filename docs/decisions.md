# 설계 결정 기록

기능 하나가 끝날 때마다 "결정 사항 / 이유 / 대안"을 남긴다.

## 1단계: 프로젝트 세팅 (2026-10-06)

### 패키지 매니저: pnpm

- **결정**: pnpm 10을 사용하고 `packageManager` 필드로 버전을 고정한다.
- **이유**: 설치가 빠르고, `package.json`에 선언하지 않은 패키지를 import할 수 없어 의존성 누락을 일찍 발견한다.
- **대안**: npm. 추가 설정이 필요 없지만 느리고, 선언하지 않은 의존성도 우연히 동작한다.
- **주의**: pnpm 10은 설치 스크립트를 기본 차단한다. Prisma와 esbuild는 `pnpm-workspace.yaml`의 `onlyBuiltDependencies`에 명시해 허용했다.

### lint / format: ESLint + Prettier

- **결정**: ESLint는 버그 가능성, Prettier는 코드 모양만 담당한다. `eslint-config-prettier`로 겹치는 규칙을 끈다.
- **이유**: Next.js 공식 ESLint 규칙과 Tailwind 클래스 정렬 플러그인을 그대로 쓸 수 있다.
- **대안**: Biome. 하나의 도구로 빠르게 처리하지만 Next.js 전용 규칙 지원이 부분적이다.

### 로컬 DB: Docker Compose + PostgreSQL 17

- **결정**: 이미지 메이저 버전을 `postgres:17`로 고정하고, 포트는 `127.0.0.1`에만 바인딩한다.
- **이유**: `latest`는 메이저 버전이 바뀌면 기존 볼륨과 호환되지 않는다. 로컬 개발 DB를 같은 네트워크에 노출할 이유가 없다.
- **대안**: PC에 PostgreSQL 직접 설치. 컨테이너가 필요 없지만 버전과 설정이 개발 환경마다 달라진다.

### 테스트 DB: 같은 컨테이너에 별도 데이터베이스

- **결정**: `studygroup_test` DB를 컨테이너 최초 기동 때 만들고, Vitest가 `DATABASE_URL`을 `TEST_DATABASE_URL`로 바꿔 넣는다.
- **이유**: 동시성 테스트(9단계)는 실제 PostgreSQL의 잠금·격리 수준 동작이 필요해 모킹으로 대체할 수 없다. 테스트가 개발 데이터를 지우는 사고도 막는다.
- **대안**: Testcontainers(테스트마다 새 컨테이너, 격리는 완벽하지만 느리고 설정이 무겁다), SQLite 인메모리(빠르지만 PostgreSQL과 잠금 동작이 달라 이 프로젝트의 목적에 맞지 않는다).

### Prisma 7: 드라이버 어댑터와 버전 고정

- **결정**: `prisma`, `@prisma/client`, `@prisma/adapter-pg`를 모두 `7.10.0`으로 정확히 고정한다. 클라이언트는 `src/generated/prisma`에 생성하고 커밋하지 않는다.
- **이유**: 세 패키지는 버전이 같아야 한다. 생성 코드는 `prisma generate`로 언제든 다시 만들 수 있어 `postinstall`에서 자동 생성한다.
- **대안**: `^` 범위 지정. 설치 시점에 따라 패키지끼리 버전이 어긋날 수 있다(실제로 겪음, `troubleshooting.md` 참고).

### 환경변수: Zod 검증

- **결정**: `src/env.ts`에서 환경변수를 Zod로 검증하고, 코드에서는 `process.env` 대신 `env`를 import한다.
- **이유**: 값이 빠졌을 때 첫 쿼리 시점이 아니라 모듈 로드 시점에, 어떤 변수가 문제인지 알려 주며 실패한다.
- **대안**: `process.env`를 직접 사용. 간단하지만 타입이 `string | undefined`이고 오류가 늦게 드러난다.

### 테스트 환경: Vitest node 환경

- **결정**: jsdom과 Testing Library 없이 node 환경으로만 구성한다.
- **이유**: 이 프로젝트의 테스트 대상은 상태 전이·권한·동시성 같은 서버 로직이다.
- **대안**: 컴포넌트 테스트 도구 포함. 필요해지는 시점에 추가한다.

## 2단계: DB 스키마 설계 (2026-10-06)

구조와 제약·인덱스 목록은 `docs/erd.md`에 있다. 여기에는 선택의 이유만 적는다.

### 중복 신청 방지: 전체 유니크 제약 (재신청 불가)

- **결정**: `applications (recruitment_id, applicant_id)`에 유니크 제약을 건다. 취소·거절된 신청이 있어도 다시 신청할 수 없다.
- **이유**: "한 번만 신청"이라는 규칙을 제약 하나로 보장하고, 동시에 들어온 중복 요청도 DB가 한 건만 통과시킨다(테스트로 확인).
- **대안**: 부분 유니크 인덱스(`WHERE status IN ('PENDING','APPROVED')`)로 재신청 허용. raw SQL이 필요하고 신청 이력이 여러 행으로 늘어난다.

### 승인 인원: 카운터 컬럼 없이 시작

- **결정**: `approved_count` 컬럼을 두지 않고, 승인 인원은 `applications`를 세어 구한다.
- **이유**: 9단계에서 "마지막 한 자리에 동시 승인이 몰리는" 문제를 먼저 재현한 뒤 해결책을 비교하기 위해서다. 정규화된 상태에서 출발해야 전후 차이가 드러난다.
- **대안**: 카운터 컬럼 + `CHECK (approved_count <= capacity)`. DB 수준 보장이 일찍 생기지만 값이 두 곳에 저장되어 어긋날 위험이 있다. 9단계의 해결책 후보로 남겨 둔다.

### 기본 키: cuid 문자열

- **결정**: 모든 테이블의 단일 기본 키는 `cuid()` 문자열이다. 연결 테이블은 복합 기본 키를 쓴다.
- **이유**: URL에서 순번을 추측할 수 없고, Auth.js 어댑터가 기대하는 형식과 같아 3단계에서 변환이 필요 없다.
- **대안**: auto increment 정수(작고 빠르지만 순번이 노출됨), UUID v7(네이티브 타입이고 시간순 정렬되지만 설정이 더 필요함).

### 다대다: 명시적 연결 테이블

- **결정**: 모집글과 태그의 관계를 `recruitment_tags` 모델로 직접 정의한다.
- **이유**: 복합 PK의 컬럼 순서와 `tag_id` 인덱스를 직접 정할 수 있고, 테이블·컬럼 이름이 ERD와 일치한다.
- **대안**: Prisma 암묵적 다대다. 코드는 짧지만 `_RecruitmentToTag (A, B)` 같은 테이블이 자동 생성되어 raw SQL에서 다루기 어렵다.

### DB 이름 규칙과 시간 타입

- **결정**: 테이블·컬럼·enum 타입을 모두 snake_case로 매핑하고, 시각은 전부 `timestamptz(3)`로 저장한다.
- **이유**: 이후 단계의 raw SQL과 `EXPLAIN`에서 따옴표 없이 쓸 수 있다. Prisma 기본값인 시간대 없는 `timestamp`는 서버 시간대 설정에 따라 마감일 판정이 달라질 수 있다.
- **대안**: Prisma 기본값 사용. `@map`이 필요 없어 스키마가 짧지만 `"authorId"`처럼 따옴표가 필요하다.

### 인덱스: 최소한으로 시작

- **결정**: 유니크 제약과 외래 키 인덱스만 만든다.
- **이유**: 인덱스는 쓰기 비용과 저장 공간을 쓴다. 13단계에서 대량 데이터로 느린 쿼리를 측정한 뒤 추가해야 필요한 인덱스만 남고 전후 수치를 기록할 수 있다.
- **대안**: 목록 필터·정렬용 인덱스를 미리 추가. 쿼리 형태가 정해지기 전이라 쓰이지 않는 인덱스가 생길 수 있다.

### 테스트 DB 마이그레이션: Vitest globalSetup

- **결정**: 테스트 시작 전에 테스트 DB의 테이블을 비우고 `prisma migrate deploy`를 실행하며, 테스트 파일은 순서대로 실행한다(`fileParallelism: false`). 테이블 비우기는 3단계에서 추가했다(`troubleshooting.md` 참고).
- **이유**: 스키마를 바꾼 뒤 테스트 DB 갱신을 잊는 실수가 없어진다. 파일들이 DB 하나를 공유하므로 병렬 실행하면 데이터 초기화가 서로를 깨뜨린다.
- **대안**: 수동 스크립트(`db:migrate:test`)는 잊기 쉽다. 워커마다 DB를 따로 두면 병렬 실행이 가능하지만 지금 규모에는 과하다.

## 3단계: 회원가입/로그인 (2026-10-06)

### 인증 라이브러리: Auth.js v5 베타 고정

- **결정**: `next-auth@5.0.0-beta.32`를 정확한 버전으로 고정해 사용한다.
- **이유**: App Router에 맞게 설계되어 서버 컴포넌트와 Server Action에서 `auth()`로 세션을 읽는다. 베타는 다음 버전에서 API가 바뀔 수 있어 `^` 없이 고정했다.
- **대안**: v4 안정판(Pages Router 시절 API라 App Router에서 번거롭다), 세션을 직접 구현(학습에는 좋지만 쿠키·서명·만료 처리의 실수 위험을 진다).

### 로그인 방식: 이메일·비밀번호 + JWT 세션

- **결정**: Credentials 로그인만 제공하고 세션은 JWT 쿠키에 담는다. Prisma 어댑터와 세션·계정 테이블은 쓰지 않는다.
- **이유**: 외부 서비스 설정 없이 테스트할 수 있고, Auth.js의 Credentials 로그인은 JWT 세션에서만 동작한다.
- **대안**: OAuth 추가(가입은 편하지만 어댑터와 테이블 3개가 필요하다), DB 세션(즉시 무효화가 가능하지만 Credentials와 함께 쓸 수 없다).
- **한계**: JWT는 서버에서 즉시 무효화할 수 없다. 그래서 데이터를 바꾸는 작업은 `requireUser()`로 DB에 사용자가 있는지 다시 확인한다.

### 세션 접근 계층: getSession / requireUser

- **결정**: 앱 코드는 Auth.js를 직접 부르지 않고 `src/server/auth/session.ts`의 두 함수만 쓴다. `getSession()`은 쿠키만 확인하고, `requireUser()`는 DB까지 확인한다.
- **이유**: 권한 확인 방식이 한 곳에 모이고, 화면 표시용 확인과 데이터 변경용 확인의 비용·신뢰도 차이가 함수 이름으로 드러난다.
- **대안**: 곳곳에서 `auth()`를 직접 호출. 간단하지만 DB 확인을 빠뜨리기 쉽고 라이브러리 교체 시 수정 범위가 넓다.
- **영향**: 헤더가 쿠키를 읽으므로 모든 페이지가 요청마다 렌더링된다(정적 페이지 없음).

### 비밀번호 해싱: Argon2id

- **결정**: `@node-rs/argon2`로 Argon2id(메모리 19MiB, 반복 2회, 병렬 1)를 쓴다. 정책은 길이(8~128자)만 검사한다.
- **이유**: OWASP가 1순위로 권장하는 알고리즘이고, 해시 문자열에 파라미터와 솔트가 함께 들어가 나중에 강도를 올려도 기존 해시를 검증할 수 있다. 문자 조합 규칙은 NIST가 권장하지 않는다.
- **대안**: bcryptjs(순수 JS지만 72바이트 제한이 있다), Node 내장 scrypt(의존성이 없지만 저장 형식을 직접 설계해야 한다).

### 중복 가입 방지: 유니크 제약 위반을 잡아서 처리

- **결정**: 가입 전에 이메일을 조회하지 않는다. 바로 삽입하고 유니크 제약 위반(P2002)을 `CONFLICT`로 변환한다.
- **이유**: "조회 후 삽입"은 두 단계 사이에 다른 요청이 끼어들 수 있다. 동시 가입 5건 중 1건만 성공하는 것을 테스트로 확인했다.
- **대안**: 조회 후 삽입. 오류 메시지를 만들기는 쉽지만 경쟁 상태가 생기고 쿼리가 한 번 더 든다.

### 계정 존재 여부 노출 방지

- **결정**: 로그인 실패는 이유와 관계없이 같은 메시지를 내고, 이메일이 없을 때도 더미 해시로 검증을 한 번 수행한다.
- **이유**: 메시지나 응답 시간 차이로 특정 이메일의 가입 여부를 알아낼 수 없게 한다.
- **한계**: 가입 화면은 "이미 가입된 이메일"이라고 알려 준다. 사용성을 위해 받아들인 노출이고, 14단계의 레이트 리밋으로 대량 조회를 막는다.

### 에러 형식: Result 타입

- **결정**: 예상 가능한 실패는 예외 대신 `{ ok: false, error: { code, message, fieldErrors } }`로 반환한다(`src/lib/result.ts`). 예상하지 못한 오류만 예외로 둔다.
- **이유**: Server Action의 반환값으로 그대로 폼에 전달할 수 있고, 호출하는 쪽이 실패 처리를 빠뜨리면 타입 오류가 난다.
- **대안**: 커스텀 예외를 던지고 한 곳에서 변환. 서비스 코드는 짧아지지만 어떤 함수가 어떤 실패를 내는지 타입에 드러나지 않는다.

### users 테이블 정리

- **결정**: `password_hash`를 추가하고 `name`을 필수로 바꿨으며, 2단계에서 넣었던 `email_verified`·`image`를 삭제했다.
- **이유**: 두 컬럼은 Auth.js 어댑터를 쓸 것으로 가정하고 넣었는데, 어댑터 없이 가기로 하면서 쓰는 곳이 없어졌다.
- **대안**: 유지. OAuth를 붙일 때 다시 필요하지만 그때 추가하는 마이그레이션은 간단하다.

## 4단계: 모집글 CRUD (2026-10-06)

### 데이터 변경의 진입점: Server Action + 서비스

- **결정**: 작성·수정·삭제는 Server Action으로 받고, Action은 "로그인 확인 → 입력 검증 → 서비스 호출 → 이동"만 한다. 권한과 상태 검증은 `src/server/recruitments/recruitment.service.ts`에 있다.
- **이유**: 폼과 바로 연결되고, 서비스가 진입점과 분리되어 있어 요청 컨텍스트 없이 통합 테스트로 검증할 수 있다.
- **대안**: REST Route Handler. HTTP 상태 코드를 직접 다룰 수 있지만 폼 연결 코드가 늘어난다. 서비스를 그대로 쓰므로 나중에 추가할 수 있다.

### 작성자 권한: WHERE 절에 조건을 넣어 한 문장으로 검증

- **결정**: 수정·삭제는 `UPDATE ... WHERE id = ? AND author_id = ? AND deleted_at IS NULL`로 실행한다. 바뀐 행이 0개일 때만 추가 조회로 `NOT_FOUND`와 `FORBIDDEN`을 구분한다.
- **이유**: "확인 후 변경"은 두 단계 사이에 글이 삭제되거나 바뀔 수 있다. 조건을 `WHERE`에 넣으면 확인과 변경이 원자적으로 일어난다. 추가 조회는 안내 문구에만 영향을 준다.
- **대안**: 먼저 조회해 작성자를 확인한 뒤 수정. 읽기 쉽지만 경쟁 상태를 따로 처리해야 한다.
- **참고**: 작성자 ID는 세션에서만 얻고, 저장할 컬럼은 서비스에서 하나씩 나열한다. 폼에 `authorId`나 `status`를 끼워 넣어도 반영되지 않는다.

### 소프트 삭제: 명시적 조건

- **결정**: 삭제는 `deleted_at`만 채우고, 모집글을 읽거나 바꾸는 모든 쿼리에 `deletedAt: null` 조건을 직접 넣는다. 조건은 서비스 파일의 상수 하나(`notDeleted`)로 공유한다.
- **이유**: 어떤 쿼리가 실행되는지 코드에 그대로 드러나고, 이후 raw SQL을 쓰는 단계에서도 같은 원칙을 적용할 수 있다. 삭제된 글이 목록·상세·수정·재삭제에서 모두 "없는 글"로 취급되는지 테스트로 고정했다.
- **대안**: Prisma 확장으로 자동 필터. 빠뜨릴 일은 없지만 동작이 숨겨지고 raw SQL에는 적용되지 않는다.

### 마감일: 날짜 입력, 한국 시간 기준 그날의 끝으로 저장

- **결정**: 날짜만 입력받아 `그날 23:59:59.999 +09:00`의 시각으로 저장한다. 날짜 변환은 `src/lib/date.ts`에 모았다.
- **이유**: 사용자는 "20일까지"로 생각한다. 시간대를 코드에 고정하면 서버가 어느 시간대에서 실행되든 판정이 같다.
- **대안**: 날짜와 시각을 모두 입력. 정밀하지만 모집글에는 과하다.

### 남의 글 수정 화면: 404

- **결정**: 작성자가 아닌 사용자가 수정 주소로 들어오면 `notFound()`로 처리한다.
- **이유**: Next 16의 `forbidden()`은 아직 실험 기능이다. 화면 접근을 막는 것은 편의이고, 실제 권한은 Action과 서비스가 다시 검증한다.
- **대안**: 실험 기능을 켜고 403 페이지 표시. 안정화되면 바꿀 수 있다.

### 검증 규칙의 위치: superRefine과 transform 분리

- **결정**: 필드 간 규칙(오프라인이면 지역 필수, 마감일은 오늘 이후)은 `superRefine`에, 값 변환(숫자, 마감 시각, 온라인이면 지역 제거)은 `transform`에 둔다.
- **이유**: Zod의 `transform`은 다른 필드에 오류가 있으면 실행되지 않아, 규칙을 거기에 두면 사용자가 오류를 두 번에 나눠 보게 된다(`troubleshooting.md` 참고).
- **대안**: 서비스에서 규칙 검사. 가능하지만 필드별 오류 메시지를 폼에 연결하는 코드가 따로 필요하다.
