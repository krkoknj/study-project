# 페이지네이션: 오프셋에서 커서로

목록 페이지네이션을 오프셋 방식으로 먼저 만들고(6단계-1), 한계를 확인한 뒤 커서 방식으로 바꿨다(6단계-2).
이 문서는 무엇이 문제였고 바꾼 뒤 무엇이 달라졌는지를 기록한다.

## 두 방식

|             | 오프셋                          | 커서                                              |
| ----------- | ------------------------------- | ------------------------------------------------- |
| 주소        | `/?page=3`                      | `/?cursor=WzE3OT…`                                |
| 뜻          | 앞에서 40건을 건너뛰고 20건     | 이 글 다음부터 20건                               |
| 쿼리        | `ORDER BY … LIMIT 20 OFFSET 40` | `WHERE (커서보다 뒤) ORDER BY … LIMIT 20`         |
| 위치의 기준 | 순번. 글이 추가·삭제되면 달라짐 | 글 자체(작성 시각, id). 다른 글이 바뀌어도 그대로 |

정렬 기준은 두 방식 모두 `(created_at DESC, id DESC)`다. 작성 시각이 같은 글이 있을 수 있어서 `id`까지 있어야 순서가 하나로 정해진다.

## 문제 1: 넘기는 사이 글이 바뀌면 중복되거나 빠진다

글 6건을 3건씩 볼 때, 1페이지(글 006, 005, 004)를 읽은 뒤의 2페이지:

| 그 사이 일어난 일      | 오프셋 방식의 2페이지           | 커서 방식의 2페이지 |
| ---------------------- | ------------------------------- | ------------------- |
| 새 글 007이 올라옴     | 004, 003, 002 (004가 다시 나옴) | 003, 002, 001       |
| 1페이지의 005가 삭제됨 | 002, 001 (003을 영영 보지 못함) | 003, 002, 001       |

6단계-1에서 왼쪽 결과를 기대값으로 하는 테스트를 먼저 만들어 문제를 고정했고, 6단계-2에서 오른쪽 결과로 기대값이 바뀌었다.
테스트는 `recruitment.service.test.ts`의 "넘기는 사이 글이 바뀌어도 중복되거나 빠지지 않는다"에 있다.

## 문제 2: 뒤쪽 페이지일수록 느려진다

### 측정 방법

- 테스트 DB에 모집글 10만 건(50건에 1건은 삭제된 글), 페이지 크기 20
- "깊이"는 몇 번째 글부터 읽는가다. 깊이 50,000은 2,501번째 페이지에 해당한다.
- SQL은 `EXPLAIN (ANALYZE, BUFFERS)`의 실행 시간을 5회 측정한 중앙값, 괄호 안은 읽은 8KB 블록 수
- 로컬 Docker의 PostgreSQL 17.11. 절대값보다 깊이에 따른 변화와 방식 간 차이를 본다.
- 다시 실행: `pnpm measure:pagination` (`scripts/pagination.measure.ts`)

### 인덱스가 없을 때

|   깊이 |       오프셋 | 커서 (범위 + OR) |
| -----: | -----------: | ---------------: |
|      0 | 15.72 (9181) |     15.50 (9181) |
|  1,000 | 21.04 (9181) |     16.69 (9181) |
| 10,000 | 23.67 (9181) |     15.87 (9181) |
| 50,000 | 32.06 (9181) |     12.60 (9181) |
| 90,000 | 48.31 (9091) |     12.35 (9091) |

두 방식 모두 테이블 전체를 읽고 정렬한다(`Limit > Gather Merge > Sort > Seq Scan`). 읽는 블록 수가 같다.
오프셋이 깊이에 따라 느려지는 것은 건너뛸 행까지 정렬 결과에 담아야 하기 때문이다.
**인덱스가 없으면 커서 방식으로 바꿔도 첫 페이지부터 15ms가 든다.** 방식을 바꾸는 것만으로는 부족하다.

### 정렬용 인덱스 `(created_at DESC, id DESC)`가 있을 때

|   깊이 |       오프셋 | 커서 (범위 + OR) |
| -----: | -----------: | ---------------: |
|      0 |     0.02 (5) |         0.02 (5) |
|  1,000 |   0.21 (105) |         0.01 (6) |
| 10,000 |  1.99 (1006) |         0.03 (7) |
| 50,000 | 10.31 (5008) |         0.03 (6) |
| 90,000 | 17.80 (9010) |         0.02 (7) |

- 오프셋은 읽는 블록이 깊이에 비례해 늘어난다. 인덱스를 처음부터 따라가며 건너뛸 행을 모두 읽기 때문이다.
- 커서는 깊이와 무관하게 블록 6~7개만 읽는다. 인덱스에서 커서 위치를 바로 찾아 그다음 20건만 읽는다.
- 깊이 90,000에서 실행 시간 약 900배, 읽는 블록 약 1,300배 차이다.

Prisma 호출 시간(네트워크 왕복과 결과 변환 포함, 7회 중앙값)으로도 같은 경향이다.

|   깊이 | 오프셋 (`skip`) |    커서 |
| -----: | --------------: | ------: |
|      0 |         1.04 ms | 1.02 ms |
| 10,000 |         4.35 ms | 1.30 ms |
| 50,000 |        15.96 ms | 1.99 ms |
| 90,000 |        24.99 ms | 1.03 ms |

오프셋 방식은 페이지 번호를 만들려고 전체 개수도 센다. 이 `COUNT`가 인덱스 유무와 관계없이 매 요청 약 13ms였다.
커서 방식은 21건을 읽어 21번째가 있는지로 다음 페이지 유무를 판단하므로 이 쿼리가 없다.

## 커서 조건을 쓰는 방법에 따라 결과가 달랐다

"커서보다 뒤에 오는 글"은 여러 방식으로 쓸 수 있다. 인덱스가 있는 상태에서 측정했다.

|   깊이 |       (a) OR | (b) 범위 + OR | (c) 행 비교 |
| -----: | -----------: | ------------: | ----------: |
|  1,000 |   0.14 (105) |      0.01 (6) |    0.02 (6) |
| 10,000 |  1.36 (1006) |      0.03 (7) |    0.03 (7) |
| 50,000 |  7.02 (5008) |      0.03 (6) |    0.02 (6) |
| 90,000 | 13.78 (9010) |      0.02 (7) |    0.02 (7) |

```sql
-- (a) 교과서에 나오는 형태
WHERE created_at < :c OR (created_at = :c AND id < :i)

-- (b) 범위 조건을 따로 둔 형태 (채택)
WHERE created_at <= :c AND (created_at < :c OR id < :i)

-- (c) 행 비교
WHERE (created_at, id) < (:c, :i)
```

**(a)는 커서 방식인데도 오프셋만큼 느리다.** 깊이 50,000에서의 실행 계획을 보면 이유가 드러난다.

```
(a)  Index Scan using recruitments_created_at_id_idx
       Filter: (… (created_at < …) OR ((created_at = …) AND (id < …)))
       Rows Removed by Filter: 50001
       Buffers: shared hit=4908

(b)  Index Scan using recruitments_created_at_id_idx
       Index Cond: (created_at <= …)
       Filter: (… (created_at < …) OR (id < …))
       Rows Removed by Filter: 1
       Buffers: shared hit=6

(c)  Index Scan using recruitments_created_at_id_idx
       Index Cond: (ROW(created_at, id) < ROW(…, …))
       Buffers: shared hit=6
```

(a)는 조건 전체가 `Filter`가 된다. PostgreSQL이 `OR`로 묶인 조건을 인덱스의 시작 지점으로 쓰지 못해서, 인덱스를 처음부터 훑으며 50,001건을 읽고 버린다.
(b)와 (c)는 `Index Cond`가 되어 인덱스에서 그 지점으로 바로 간다.

(c)가 가장 깔끔하지만 Prisma의 `where`로는 행 비교를 쓸 수 없어 raw SQL이 필요하다. (b)는 Prisma로 표현할 수 있고 성능이 같아서 (b)를 택했다.
구현은 `recruitment.service.ts`의 `afterCursor`에 있다.

## 커서 방식으로 바꾸며 잃은 것

- **전체 개수와 "N / M 페이지" 표시**가 없다.
- **특정 페이지로 바로 이동**할 수 없다. "다음"과 "처음으로"만 있고, 이전 페이지는 브라우저의 뒤로 가기로 간다.
- **정렬 기준을 바꾸기 어렵다.** 커서, 정렬, 인덱스가 같은 컬럼 조합이어야 한다. 마감일순 정렬을 추가하려면 커서 형식과 인덱스가 하나씩 더 필요하다.

모집 게시판은 최신 글부터 훑어보는 용도라 이 제약을 받아들였다. 관리자 화면처럼 "37페이지로 이동"이 필요한 곳이라면 오프셋이 맞다.

## 아직 측정하지 않은 것

이번 측정은 **필터가 없는 기본 목록**이 대상이다. 유형·태그·모집중 필터가 걸리면 조건에 맞는 글이 드문 경우
인덱스를 따라가며 많은 행을 읽고 버릴 수 있다. 필터 조합별 실행 계획과 인덱스는 13단계에서 다룬다.
